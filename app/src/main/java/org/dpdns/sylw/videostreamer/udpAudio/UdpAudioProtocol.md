# UDP 音频传输协议设计文档

## 双重连接机制

音频传输建立两个独立连接，分别用于：
1. **TCP 连接 (可靠性)**：用于握手、配置同步、状态反馈及心跳检测。
2. **UDP 连接 (实时性)**：用于连续的 PCM 音频数据流。

连接状态依 TCP 确认，其中一方断开 TCP 连接即视为音频服务彻底断开。


## 1. 握手与控制阶段 (TCP)
客户端连接服务端 TCP 端口后，首先发送 1 个固定 6 字节配置包。TCP 是字节流，接收端必须读满 6 字节后再解析，不能假设一次 `read` 就得到完整配置包。
| 字段 | 长度 | 说明 |
| :--- | :--- | :--- |
| **协议版本** | 1 Byte | 当前为 `0x01` |
| **采样率索引** | 1 Byte | 0x01 (48000Hz)  0x00 44100
| **声道数** | 1 Byte | 0x02 (立体声)  0x01 单声道
| **编码格式** | 1 Byte | `0x00` PCM，`0x01` Opus |
| **编码帧长** | 1 Byte | 单位 ms；PCM 模式忽略此值；Opus 当前允许 10 / 20 / 40 |
| **Opus 码率** | 1 Byte | 单位 kbps；PCM 模式忽略此值 |

在收到服务端空包确认后，连接建立。
TCP 链路后续用于：

- 心跳检测与延迟测试：客户端记录（不发送）音频包时间戳，服务端主动发包或回包格式如下：
  | 字段 | 长度 | 说明 |
  | :--- | :--- | :--- |
  | **总长度** | 2 Bytes | 大端序，含头部自身在内的总字节数 |
  | **[序号 + 接收时间戳] × N** | 9 × N Bytes | 每条：1 字节序号 + 8 字节 UDP 包接收时间戳（大端序，ms） |
  | **回包时间戳** | 8 Bytes | 服务端发包时间戳（大端序，ms） |

  包可能不携带任何序号条目（N=0），此时总长度为 10。时间戳单位为 ms，建议使用 Unix 纪元起点。服务端发的接收时间戳不一定有效，当计算得到的最小延迟小于 -20ms 时认为无效。
- 状态反馈。

## 2. 数据传输阶段 (UDP Payload)
每帧音频数据根据握手中的编码格式解释。开启冗余时，每帧数据发送 3 次冗余包：
| 字段 | 长度 | 说明 |
| :--- | :--- | :--- |
| **序号** | 1 Byte | 0x00 - 0xFF (循环递增) |
| **音频数据** | N Bytes | PCM 模式为原始 PCM 分片；Opus 模式为一个完整裸 Opus access unit |

### PCM 模式
PCM 使用 16-bit little-endian 交错采样数据。客户端会按 MTU 分片，接收端按序号去重、按到达顺序播放。

### Opus 模式
Opus 使用 Android `MediaCodec` 产出的裸 Opus access unit，不封装 Ogg/WebM。客户端会把 AudioRecord 读到的 PCM 累积到握手声明的帧长后再编码，因此组帧新增延迟小于 1 个 Opus 帧长。Opus 模式不在应用层拆包，每个 UDP 包携带一个完整 Opus access unit；若单帧超过路径 MTU，由 UDP/IP 下层处理。建议默认：

- 帧长：20 ms，低延迟优先时可选 10 ms
- 码率：32 kbps 起，根据声道数和音质需求调整

接收端必须根据握手中的采样率、声道数、帧长和码率初始化 Opus 解码器，并按 UDP 包序号去重、丢包检测和顺序播放。

## 3. 冗余与处理
- **包三送**: 每帧数据连续发送 3 次相同序号的数据包。
- **接收端处理**: 结合 TCP 连接状态，丢弃重复及乱序包，利用序号进行丢包检测。
